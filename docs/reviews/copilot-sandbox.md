# Copilot shell sandbox completion

Reviewed and completed the interrupted opt-in shell sandbox implementation. `tools.command_sandbox` remains disabled by default; `sandbox_runtime` selects an installed Docker or Podman client and `sandbox_image` names an already available image. `--pull=never` prevents an implicit image download. If the selected runtime is absent or configuration is invalid, no host-command fallback occurs.

The shell invocation fixes its entrypoint to `sh`, keeps the existing command approval and block policy, and validates image references and bind-mount source delimiters before launch. Containers run as the host's non-root UID/GID (or the existing non-root numeric default where Unix IDs are unavailable), with no network, read-only image filesystem, dropped capabilities, no-new-privileges, process/memory/CPU limits and a bounded temporary filesystem. No host environment variables are passed into the container. The project is intentionally mounted read-write; project data, including private project files, remains available to the command. Commands and image contents remain operator-trusted; this is not a guarantee against runtime vulnerabilities or a misconfigured daemon.

Timeout/cancellation reaps the owned client process tree through the existing process helper and requests force-removal of the exact random container name. Cleanup has its own deadline; failure is visible in timeout/error results or cancellation diagnostics. Timed-out or otherwise uncertain execution is marked `execution_outcome=unknown` and `mutation_completion_unknown=true`, so callers can avoid replaying potentially applied edits. Ordinary completed commands retain their exit code even if output contains invalid UTF-8.

## Verification

The focused sandbox/approval/safety/config/harness-mode run passed **69 tests**; compilation and whitespace checks passed. Focused tests cover restricted arguments, explicit approvals, missing runtimes, image option injection, mount delimiter rejection, root UID rejection, configuration forwarding, binary output, timeout bounds and cleanup failure diagnostics. Real disposable fake-runtime subprocesses verify that timeout/cancellation, including cancellation before the process handle is returned, reaps the client PID and requests removal of the same container name. Those lifecycle fixtures do not provide evidence of real Docker/Podman isolation. No image was pulled and no external target was contacted.

The feature still applies only to `run_command`; dedicated test/build/formatter/scanner processes are outside this sandbox setting. It is not a transactional rollback facility and cannot reverse previous command effects or concurrent workspace edits. Native Windows/macOS and real container filesystem/network enforcement require separate integration evidence. Docker/Podman daemon selection and configuration remain the operator's responsibility; a configured remote daemon is not made local by this setting.
